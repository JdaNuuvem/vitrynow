# Runbook de infraestrutura (INF-11, versão inicial) · DEV e staging local

Só DEV/staging local. **Nada aqui foi aplicado em produção** e produção exige aprovação explícita do Claudio.
Cada procedimento diz se foi **provado por execução** (com o arquivo que prova) ou está **pendente**. Onde não provei, não afirmo.

## 1. A stack em uma frase
Só o **Caddy** publica portas (80/443). `web` e `api` ficam na rede de borda; o `postgres` (e `migrate`, `postgres-backup`) ficam na rede `data`, **interna** (sem saída à internet, e o Caddy e o web não a enxergam). O Caddy tem IP fixo (`CADDY_IP`), e a API só confia no `X-Forwarded-For` desse IP (`TRUST_PROXY_CIDR` é derivado, não se define). Prova: `scripts/smoke-stack.sh`.

## 2. Antes de subir (sempre)
1. `cp infra/.env.example infra/.env` e preencha. Gere segredos com `openssl rand -hex 32` (Postgres: `openssl rand -hex 24`, **só** `[A-Za-z0-9_-]`; base64 quebra a `DATABASE_URL`). Cada segredo é **diferente**.
2. `infra/check-env.sh infra/.env`: recusa segredo curto/igual/de exemplo, URL sem https, `COOKIE_SECURE=false`, `TRUST_PROXY_CIDR` definido, PIX incompleto. Nunca imprime valores. **Provado:** `scripts/test-check-env.sh` (43 casos no Linux, sem Docker). Para PRODUÇÃO use `infra/check-env.sh --prod` (o `deploy.sh` já usa): MFA_ENFORCED != true, `APP_VERSION=local` e `RESEND_API_KEY` vazia viram ERRO; `ADMIN_TOKEN` preenchido com menos de 32 caracteres é erro sempre; `.env` legível por outros dá aviso de `chmod 600` (só em Linux).
3. Só então `docker compose --env-file infra/.env -f infra/docker-compose.yml up -d --build`. O compose também recusa `.env` sem `JWT_SECRET`, `MFA_HMAC_KEY`, `API_INTERNAL_SECRET`, `POSTGRES_PASSWORD`, `WEB_ORIGIN` (**provado** no smoke, seção 8).

## 3. Atualizar e voltar (rollback)
- A imagem leva `APP_VERSION` (use o hash curto do commit). O serviço `migrate` aplica as migrações **antes** da API subir (`service_completed_successfully`): se falhar, a API antiga continua no ar. **Provado:** smoke (migrate exit 0, N/N migrações).
- Voltar: suba de novo com a `APP_VERSION` anterior (as imagens ficam no disco). **O banco NÃO volta junto**: migração aplicada fica aplicada. Por isso migração destrutiva é separada em expand → migrar dados → contract em release posterior (regra do Atlas) e há backup verificado antes.
- Carimbo de migração: único e crescente; `scripts/check-migrations.sh` reprova repetido/decrescente. **Provado** (`scripts/test-stamps.sh`; caso real da API-12).

## 4. Uma migração falhou (Prisma P3009)
Sintoma: o `migrate` sai com erro e novos deploys dizem *"found failed migrations"*. A migração roda numa transação: **nada fica pela metade**.
1. Leia a mensagem. Ex. real (SEC-20): `E-mails duplicados ao normalizar (resolva manualmente antes; nada foi alterado): fulano@x (2 contas)`.
2. Corrija o **dado** (decisão do produto; a migração nunca apaga nada).
3. Marque a migração como não aplicada: `prisma migrate resolve --rolled-back <nome-da-migração>`.
4. Rode o deploy de novo. **Provado** com o Prisma direto num banco descartável (`scripts/check-migrations.sh`, cenário S7, `INF-07-sec20-email-lower.log`). **Não executei** o mesmo comando por `docker compose run --rm migrate …`.

## 5. Backup e restauração
- O serviço `postgres-backup` roda `scripts/backup/backup.sh` a cada 24 h: **recusa banco sem tabelas** (o B05), confere o dump, grava `.sha256`, só então aplica retenção; modo 700/600. Backup manual: `docker compose exec postgres-backup /bin/sh /scripts/backup.sh`.
- Provar a restauração: `scripts/backup/restore-verify.sh <dump>` restaura num banco **novo** e confere sha256, migrações e contagem linha a linha. **Provado:** `scripts/test-backup-restore.sh` (10 verificações; a suíte inteira da API roda verde sobre o banco restaurado: 251 testes).
- **Ressalvas:** (a) o backup está no **mesmo servidor**: cópia off-site depende de destino que só o Claudio define (CL-12); (b) criptografar o backup antes do off-site (recomendação da Nightingale, não feito); (c) o volume `caddy_data` (conta ACME) **não** entra no backup: é segredo, trate à parte.

## 5b. ANTES de restaurar um backup: exportar o que é IRREVERSÍVEL (INF-11; Nightingale A2, Leonardo A2b)
**Regra:** restaurar um dump anterior **ressuscita** dado que o sistema já apagou ou anonimizou (nome, telefone e endereço de cliente anonimizado, API-52a), **e a linha de `AuditLog` que registrava a anonimização some junto** (está no mesmo banco). Por isso, antes de QUALQUER restauração (no servidor ou em ensaio com dado real):
1. Exportar do banco ATUAL as linhas irreversíveis (somente leitura; o arquivo tem ids opacos, sem dado pessoal; guardar fora do banco, modo 600):
   `docker compose exec -T postgres psql -U meucardapio -d meucardapio -At -c "COPY (SELECT id, \"storeId\", action, \"targetType\", \"targetId\", metadata, \"createdAt\" FROM \"AuditLog\" WHERE action = 'privacy.anonymize_customer' ORDER BY \"createdAt\") TO STDOUT WITH CSV HEADER" > anonimizacoes-AAAAMMDD.csv`
   (a ação passa a existir quando a API-52a entrar na main; antes disso a consulta volta vazia. Para outras ações irreversíveis futuras, acrescentar o nome em `action IN (...)`.)
2. Restaurar (e só então migrar: `prisma migrate deploy`).
3. **Reaplicar**: para cada `orderIds` em `metadata` do CSV (a API-52a grava os ids; lotes de até 500 por linha), rodar de novo a anonimização desses pedidos e conferir que nome/telefone/endereço voltaram a ficar vazios. Sem o CSV não há como saber quem foi anonimizado.
4. Registrar no BOARD/runbook de incidentes: dump usado, data, CSV, quantos pedidos reaplicados.
**Limites (honestos):** a retenção é `KEEP_DAYS=14` e `KEEP_MIN=3` (nunca apaga os 3 mais recentes): o dado anonimizado continua nos backups por até 14 dias (o aviso de privacidade precisa dizer isso; é do jurídico). A reaplicação por `orderIds` ainda **não existe como comando** (depende da API-52a gravar `orderIds`); até lá o passo 3 é manual. Provado: a consulta roda (Postgres de teste, 17/11) e devolve o cabeçalho CSV. NÃO provado: contra uma anonimização REAL (não existe ainda) nem a reaplicação.

## 6. PIX por loja (API-07)
- Padrão: `MP_OAUTH_MODE=off` (nada do PIX é exigido). Para `real`: `PAYMENT_ENC_KEY` (32+, própria), `PAYMENT_ENC_KEY_ID`, `MP_CLIENT_ID`, `MP_CLIENT_SECRET`, `PUBLIC_API_URL` (https). `fake` só em dev. `infra/check-env.sh` valida; a API recusa subir fora disso.
- **Rotação da chave de cifra** (sem queda): (1) ponha a nova em `PAYMENT_ENC_KEY` com `PAYMENT_ENC_KEY_ID=v2` e a antiga em `PAYMENT_ENC_KEY_PREV` + `PAYMENT_ENC_KEY_PREV_ID=v1`; (2) `check-env.sh` e deploy; (3) **re-cifrar tudo** com a chave nova; (4) só depois esvazie os dois `PREV` e faça o deploy.
- **PENDENTE:** o passo (3). `StorePaymentsService.reencryptAll(keyId)` existe e é idempotente (testado pelo Babbage), mas **falta o comando/CLI**: sem ele este passo não é executável. Dono: Babbage/Turing. Não ligue `MP_OAUTH_MODE=real` antes de P-1..P-5 (condição G3).
- **Trocar de vendedor do Mercado Pago (decisão do Atlas, parecer da Nightingale):** sem pendências a troca é permitida; com PIX/estorno pendente a API **bloqueia** (409 `MP_HAS_PENDING_PAYMENTS`; reconectar a MESMA conta passa). **Limite conhecido:** os pagamentos antigos já encerrados ficam presos à conta `DISCONNECTED`, sem tokens. Um estorno **tardio** desses pedidos **só sai pelo aplicativo do próprio Mercado Pago**, não pelo sistema. Oriente o lojista antes da troca (o painel mostra o aviso, texto do Leonardo). Suporte: se pedirem estorno de pedido antigo depois da troca, a resposta é o app do Mercado Pago.
- **PENDENTE (P-5, depende de Babbage/Turing):** perda do `refresh_token` rotativo (o Mercado Pago troca o token a cada renovação; se a gravação falhar depois da troca, a conta vira `NEEDS_RECONNECT` e o lojista precisa reconectar), renovação do token e o que fazer se ela falhar. Escrever o procedimento só quando o comportamento existir e puder ser executado.
- **Ambiente:** `NODE_ENV` ausente na API conta como **produção** (fake e `http` recusados). O compose fixa `NODE_ENV=production`; em dev o `pnpm dev` define `development`.

## 7. Segredo de serviço web→API (SEC-24)
`API_INTERNAL_SECRET` igual nos dois serviços, só em tempo de execução (nunca `NEXT_PUBLIC_*`). **Provado:** mesmo hash nos dois containers, ausente da config da imagem e dos arquivos que o navegador baixa, e o web não recebe nenhum outro segredo (smoke 6d/6f). O Caddy **remove** `x-internal-service-secret` e `x-visitor-ip` vindos da internet (smoke 6e, com controle). Rotação: novo em `API_INTERNAL_SECRET`, antigo em `API_INTERNAL_SECRET_PREVIOUS` por um deploy, depois esvazie.

## 8. Caddy (INF-18)
- Compilado com `xcaddy` a partir de `infra/caddy/Dockerfile`: imagens por **versão + digest**, módulo `caddy-ratelimit` por **commit**. Para atualizar, mude a versão/digest/commit conscientemente, rode o smoke e registre no BOARD `caddy version`, `caddy build-info` e o id da imagem final.
- Limite por IP real em `/loja/*` (120/min; IPv6 agrupado em /64). Atrás de **CDN/balanceador** todos os visitantes chegam com o IP dele e **dividem** os 120/min (ST-46): antes de qualquer CDN é preciso a lista de IPs dele em `trusted_proxies`, **o que exige nova revisão da Nightingale** (SEC-24 e `TRUST_PROXY_CIDR`). **Sem registro AAAA no piloto.**
- Não cobre ataque **distribuído** (muitos IPs): a validação do slug e o teto de obsolescência do web são a barreira principal.
- **Memória do limitador (ST-50, risco ACEITO pelo Atlas em 17/11):** medido **6 a 7 KB por IP distinto** na janela de 1 min (4 medições: 6,3 a 7,3 KB). `mem_limit: 768m` e `GOMEMLIMIT=600MiB` (teto, não reserva; custo só de RAM): cabem ~90 mil IPs a 80%. Era 512 MB, mas sob rotatividade alta de IPs o Caddy chegou a ~450 MB e o critério de 60 mil IPs passou só na margem (e falhou numa rodada: 59 mil). Um ataque com dezenas de milhares de IPs é distribuído: trata-se na borda/CDN, não aqui. **Sintoma:** o Caddy é morto por falta de memória e volta em segundos (`restart: unless-stopped`); durante esses segundos o site não responde. Se acontecer: `docker compose ps caddy` (reinícios), `docker inspect -f '{{.State.OOMKilled}}' <container>` e o tráfego por IP.
- **RISCO ABERTO (crescimento lento, não explicado):** no experimento isolado (`scripts/st50-levas.sh`; resultados em `hopperevidenciasST-50-levas.md`) as chaves vencidas são em boa parte liberadas e o resto é heap retido pelo Go, mas a memória continuou subindo devagar nas levas seguintes; **não distingui** fragmentação, cache do `docker stats` e um vazamento pequeno do módulo. **Sinal para agir:** `docker stats` do Caddy **acima de 80% do teto (≈ 615 MB de 768 MB) por mais de 10 min** com tráfego normal: reinicie o container (`docker compose restart caddy`; corta as conexões por segundos) e avise o Hopper/Atlas. O critério do smoke para a 2ª leva (falha se somar >= 80% do bloco) foi **escolhido depois de ver o número** (disclosure ao Deming): só pega o caso "nada é liberado", não prova ausência de vazamento pequeno.
- **Alerta (pendente, NG-12/INF-08; condição (a) da Nightingale):** avisar quando o container do Caddy **reiniciar**, ficar `OOMKilled`, ou passar de **70% do `mem_limit`**. Acrescentar **CPU e latência** do Caddy: o sintoma de um ataque de muitos IPs pode ser **lentidão** (o Go coletando lixo sem parar), não queda. Ainda não existe monitoramento: hoje só se vê ao olhar `docker stats`.
- **Alerta de reinício da API (pendente, NG-12; decisão do Atlas):** o **reinício do container da `api`** (`RestartCount` subindo, ou estado `Restarting`) é o sinal de que a guarda de boot derrubou a API (hoje: **fuso do Postgres fora de UTC**, SEC-32; também banco fora do ar, segredo ausente). A API sai com erro e o `restart: unless-stopped` a sobe de novo em **crash loop visível**; o Caddy responde 502. **Provado com `docker compose` real em 17/11 (serviço de teste, não a nossa API):** `up -d` **sem** `--wait` sai com 0 mesmo em crash loop; `up -d --wait` sai com **1 em ~4 s** ("container is unhealthy") e o log mostra o erro. Não existe monitoramento que avise isso hoje.
- **Deploy (`infra/deploy.sh`, INF-19):** valida o `.env` com o `check-env.sh`, faz o backup verificado, constrói, sobe com `up -d --wait --wait-timeout $DEPLOY_WAIT` (padrão 180 s) e, se a pilha não ficar saudável, **FALHA mostrando o estado dos serviços e o log do `migrate` e da `api`**, com a causa provável (fuso do Postgres) e o rollback. Avisa (sem reprovar) se a API reiniciou durante a subida. **Testado só com `docker`/`curl` falsos (`scripts/test-deploy.sh`, 17 verificações) e a premissa do `--wait` com um compose de teste real; NUNCA executado num servidor nem sobre a nossa pilha.** O Caddy não tem `depends_on` e fica como está (502 enquanto web e API sobem).
- **Retenção dos logs do Docker (ST-73):** os 6 serviços usam `json-file` com `max-size: 10m` e `max-file: 5` (até ~50 MB por serviço; o arquivo mais antigo é apagado ao rotacionar). **Não existe retenção por TEMPO** (quantos dias o log vive depende do volume de tráfego) e o log de cada linha carrega o **IP do visitante, que é dado pessoal (LGPD)**. **Decisão pendente do dono do produto:** o prazo em dias e se o IP deve ser mascarado; eu não defini nem afirmo um prazo.
- **Mitigação PREVISTA para produção (decisão do Atlas; condição (b) da Nightingale): reinício semanal do Caddy** em janela de baixo movimento, **avisado** aos lojistas, com conferência do `/health` depois (`docker compose restart caddy`; corta as conexões por segundos e zera o estado do limitador: todo IP volta a ter o balde cheio, aceitável). **Não está implementado** e **não há tarefa agendada** em nenhuma máquina: quem agendar será o servidor de produção, no dia do deploy, com aprovação do Claudio. Hoje (DEV) vale só o sinal de ação da linha acima.
- **O que esperar se a memória passar do `GOMEMLIMIT` (condição (c) da Nightingale):** o limite do Go é **soft**: se a memória VIVA passar do teto, o Go não mata o processo, passa a coletar lixo sem parar (CPU alta, respostas lentas). O sintoma de um ataque de muitos IPs pode ser **lentidão**, não queda. (Consistente com o que medi: a memória passou do `GOMEMLIMIT` sem o container cair; **não medi** CPU nem latência nesse estado.) **CDN/WAF na frente antes de escalar** (condição (d)).
- **Versão do módulo e causa do crescimento, por LEITURA do repositório `mholt/caddy-ratelimit` (17/11, nada executado):** meu commit travado `5625512f24f6` (12/06/2026) **é a ponta do `master`**: não existe commit nem versão mais nova (a única tag é `v0.1.0`, mais antiga); o único PR aberto (#98) é um limitador de concorrência, não trata memória. Não há issue aberta sobre vazamento. O código **descarta** chaves vencidas: a varredura (`sweep`) apaga do mapa a chave cujo evento mais recente saiu da janela. O custo por chave é um buffer circular de **tantas posições quanto `events`** (o mantenedor, na issue #44, atribui memória alta a isso, não a vazamento): **reduzir `events` reduz a memória por chave quase na mesma proporção**. **Isto NÃO explica nem prova a causa do crescimento lento que medi**: o código descarta, então pode ser retenção de memória do alocador do Go (fragmentação) e não vazamento do módulo; eu **não** medi o heap do Go (não rodei profile). Sem versão nova para testar, não fiz PoC.
- **Imagem do Caddy:** a versão por digest congela também os pacotes do Alpine. **Reconstrua periodicamente** (troque o digest conscientemente) e rode um scanner de vulnerabilidades (trivy ou grype) **antes de cada release**; isso **não está automatizado e não foi feito**. O `go.sum` das dependências Go não fica no repositório: a trilha é `caddy build-info` + digest, registrados no BOARD a cada mudança.
- **Logs do Caddy e segredos (NG-16, C1; CORRIGIDO em 17/11):** há DOIS caminhos. **(1) Log de ACESSO:** não existe (o Caddyfile não tem `log` de site); confere o smoke (seção 10). **(2) Log de ERRO** (`http.log.error`, existe SEM nenhuma diretiva `log`): com o web ou a API fora do ar (reinício, deploy, queda), o Caddy 2.11.9 **gravava o objeto `request` inteiro**: `?token=` da query, tokens no CAMINHO (QR de mesa `/loja/<slug>/m/<token>`, link de acompanhamento) e cabeçalhos custom (`x-order-token`, `x-mfa-challenge`, `x-admin-token`) **em claro**; só Authorization/Cookie/Set-Cookie/Proxy-Authorization saíam `REDACTED`. **Medido por mim em 17/11** (`INF-19-log-erro-caddy-bruto.log`). **Minha afirmação anterior de que "o Caddy não registra a URL" estava incompleta: valia só para o log de acesso.** A pilha mesclada na main (H1/INF-18/INF-09) **tinha** esse vazamento; a correção é a INF-19.
- **Filtro do log de erro (INF-19):** o `log` global do Caddyfile aplica um filtro **seguro por padrão** (não é lista negra) ao logger PADRÃO: apaga `request>headers` inteiro e reduz `request>uri` ao primeiro segmento do caminho sem query (`/reset-senha/REDACTED`); `resp_headers` e `headers` também são apagados, **por defesa** (nenhum cenário medido gravou esses campos). Provado: upstream fora do ar (smoke, seção 11) e resposta abortada no meio (`http.handlers.reverse_proxy`, isolado): nenhum dos valores únicos aparece, e o log de erro continua existindo (status 502 e a mensagem). **Limites:** um `log` de SITE tem encoder próprio e **não herda** este filtro (quem ligar log de acesso precisa repetir o filtro lá, com controle positivo); o filtro também remove informação útil para depurar (cabeçalhos e o caminho completo); medi só dois cenários (upstream fora do ar e resposta abortada).
- **Se o Caddy ganhar `trusted_proxies`** (CDN/ST-46): a SEC-24 e o `TRUST_PROXY_CIDR` precisam de nova revisão da Nightingale.
- **Estado:** smoke da stack real em 17/11, **topo final da pilha INF-09 `44c576e` (com mem_limit 768m, GOMEMLIMIT 600MiB e a 2ª leva de chaves): 60 ok / 0 falhas** (`INF-09-smoke-pilha-mem768.log`; depois só o runbook mudou). Rodadas anteriores: INF-18 `ae4c313` 56 ok / 0 (mem 512 MB); pilha `053d289` 59 ok / 1 falha (o teto de 512 MB sustentou ~59 mil IPs; motivou os 768 MB). ST-50 com 768 MB: 6,4 KB por chave; o teto sustenta ~100 mil IPs a 80%; a 2ª leva somou +70 MB (57% do bloco), o que o critério aceita **com aviso**. O crescimento lento continua **risco aberto** (acima).

## 9. Docker Desktop caiu (ambiente DEV)
Sintoma: suítes falham em massa com `Can't reach database server`/503; `docker info` falha. **Não é código.**
1. Confira se o app Docker Desktop está rodando; se não, abra `%LOCALAPPDATA%\Programs\DockerDesktop\Docker Desktop.exe`.
2. Espere o motor (≈1–2 min) e suba o seu Postgres de teste: `docker start mc-test-<agente>-<porta>` e espere `pg_isready` (≈1 min de recuperação).
3. Só rode suítes depois (no máximo 2 completas ao mesmo tempo, regra do BOARD §0).
Histórico e contexto medido: BOARD §3 (5 saídas em 17/11; causa **não provada**).

**Regra de infra de testes (Atlas, 17/11; incidente com um falso vermelho no smoke):** **ninguém reutiliza a imagem ou o container de outro agente** em experimento. A imagem `meucardapio-web:smoke` carrega o rótulo `com.docker.compose.project=mc-smoke-hopper` e **todo `docker run` dela herda o rótulo** (provado), o que fez um container de medição da Tesla passar pelo filtro do meu smoke. Use **imagem própria, sem rótulos de projeto** (confira: `docker image inspect <img> --format "{{.Config.Labels}}"` deve dar vazio), e publique portas **só em `127.0.0.1`**, nunca em `0.0.0.0`. Dois smokes ao mesmo tempo também colidem na sub-rede fixa (pendente na INF-19).

## 10. Modo de impressão por loja, LEGACY ou QUEUE (API-12b, ADR-0004 §8.12)
**O que eu verifiquei:** só a migração `20261117160000_store_print_mode` (21 ok / 0 falhas; junto com a API-07, 37 ok / 0 falhas; `hopper\evidencias\INF-07-api12b-160000.log`): aditiva, as lojas existentes viram LEGACY. **O que é relato do Turing/Atlas e eu NÃO executei:** o comportamento da virada abaixo.
- **CONDIÇÃO ANTES DE QUALQUER TROCA PARA QUEUE (decisão do Atlas, achado do Ritchie na PC-22):** a API-12b e o cliente da **PC-22** entram **juntos na mesma janela**, e **nenhuma loja pode virar para QUEUE com um print-client anterior à PC-22**. O motivo: em QUEUE a lista legada `/api/device/orders/pending` devolve **200 com lista vazia** (não erro), então um cliente antigo nunca descobre a fila e **a cozinha fica sem tíquete**, sem nenhum alarme. A PC-22 faz o cliente ler `GET /api/device/config` (`{mode}`) a cada ciclo e trocar sozinho. **Hoje o sistema não impede isso** (a recusa automática de virar QUEUE com cliente antigo ficou para depois; o painel das impressoras deve mostrar a versão do cliente, P2, ainda não existe). Antes de virar uma loja: **confira à mão a versão do print-client instalado nela**. Esta é uma regra de operação, não uma trava.
- **Trocar o modo:** `PUT /api/store/print-mode`, só o OWNER. Faça **fora do horário de pico**. A resposta traz as **3 consultas de conferência**: depois da virada devem dar **0**. Repetir a troca é seguro (idempotente: não muda nada nem grava nova auditoria). Se as consultas não zerarem, **pare e avise o Turing/Atlas**: não force.
- **QUEUE para LEGACY (recuo de emergência):** é recusado com 409 `PRINT_IN_PROGRESS` enquanto houver job em impressão com lease vigente (lease de 120 s). O painel diz "há impressão em andamento, tente em instantes": espere **até 2 min** e repita.
- **Auditoria:** cada troca grava `print.mode_change` na mesma transação (se não grava, o modo não muda); STAFF recebe 403 e a tentativa fica registrada.
- **Voltar o app para uma versão sem esta migração:** o app antigo ignora a coluna. Desfazer o banco só **depois** de voltar o app: `ALTER TABLE "Store" DROP COLUMN "printMode"; DROP TYPE "PrintMode";`. Isso **perde o modo escolhido por loja** (volta tudo para o comportamento LEGACY). Não executado por mim.

## 11. Logs da API: o que mudou com a NG-16 (para alertas e busca, NG-12/INF-08)
**Relato do Atlas sobre `feat/NG-16-token-do-pedido` @6b5a391; eu não executei nem li o código.**
